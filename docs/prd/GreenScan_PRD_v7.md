# GreenScan PRD Agent Directive v7

## 문서 목적과 우선순위

이 문서는 GreenScan의 API 명세, DB 설계, 백엔드 모듈, 프론트엔드 흐름, 테스트와 구현 계획을 만들거나 검토하는 에이전트의 최상위 지시문이다.

- 기준 문서: GreenScan PRD v4 기반 사람용 상세 설명본 v6
- 이번 버전: v7
- v7의 핵심 변경: v6의 LiDAR 공간 스캔 MVP를 제거하고, 웹 기반 수동 공간 입력과 Vision API 후보 분류를 MVP 기본 경로로 확정한다. 원본 사진은 서버에 영구 저장하지 않는다.
- LiDAR, RoomPlan, iOS 앱은 시간이 남을 때만 검토하는 후속 확장 기능이다.

에이전트는 아래 원칙을 반드시 따른다.

1. 본 문서의 v7 결정이 v6의 LiDAR 관련 요구보다 우선한다.
2. 바뀌지 않은 v6 핵심 범위는 유지한다. 대표 공간 1개, 지원 건물, U값과 HDD 계산, 사용자 확정, 결과 표현은 유지 대상이다. 단, MVP는 진단 이력과 원본 사진을 서버에 저장하지 않는다.
3. 기준이 모호할 때 그럴듯한 수치나 정책을 임의로 확정하지 않는다. 필요한 값은 정책 확정 필요로 분리하고 DB에서 버전 관리할 수 있게 설계한다.
4. 사진 AI는 후보 분류기다. AI 원본 응답이나 모델 신뢰도만으로 계산값을 확정하면 안 된다.
5. 실제 U값, 단열재 상태, 구조 안전성, 누수 원인, 건물 전체 에너지 사용량을 사진만으로 진단하는 것처럼 구현하거나 표현하지 않는다.
6. 비용, 견적, 공식 인증, 건물 전체 진단, 상가 지원을 새 기능으로 추가하지 않는다.
7. 계산은 서버 계산 엔진이 수행한다. 프론트엔드는 계산식을 중복 구현하지 않는다.
8. MVP에 GPU 서버, 자체 모델 학습, YOLO, 벡터 DB, LangChain, Redis 또는 Celery를 기본 전제로 넣지 않는다.

## 1. 제품 정의

### 1.1 한 줄 정의

GreenScan은 노후 단독·다가구주택 및 아파트의 대표 공간 1개를 대상으로, 사용자가 입력한 공간 정보와 창호·벽체 사진의 AI 후보 분류를 결합해 추정 연간 열손실과 그린리모델링 개선 우선순위를 제시하는 전문가 진단 이전 단계의 1차 사전진단 서비스다.

### 1.2 사용자가 얻는 것

- 대표 공간 1개 기준의 창호와 외기 접촉 벽체 연간 전도 열손실 추정치
- 창호 개선, 벽체 개선, 복합 개선 등 2~3개 시나리오의 추정 감소량과 절감률
- 추정 열손실 감소량이 큰 순서의 개선 우선순위
- 사진상 이상 흔적 후보에 대한 별도 현장 점검 권장 안내
- 결과에 사용된 사용자 입력, AI 후보, 기준 데이터 버전, 계산 근거

### 1.3 절대 표현 금지

- 건물 전체 에너지 사용량 또는 고지서 사용량을 정확히 예측, 보정, 검증했다.
- 공식 에너지 등급 또는 법적 적합성 판정을 제공한다.
- 사진 AI가 실제 U값, Low-E 여부, 단열재 유무, 구조 안전성, 균열이나 누수 원인을 확정했다.
- 사진상 이상 흔적 후보 때문에 열손실 수치가 자동으로 증가했다.
- 한 방 결과가 아파트 세대 전체 또는 건물 전체 결과다.

결과 이름은 GreenScan 추정 연간 열손실 분석 또는 이와 동등하게 비공식 추정치임을 드러내는 표현을 쓴다. 근거 없는 낮음, 보통, 높음 위험도 등급은 표시하지 않는다. 결과 화면에는 이 방 기준을 명시한다.

## 2. v6에서 바뀐 MVP 범위

### 2.1 기본 사용자 흐름

1. 사용자가 건물 유형과 대표 공간을 선택한다.
2. 사용자가 대표 공간의 가로, 세로, 높이, 창호 합산면적, 외기 접촉 벽체 합산면적을 입력한다.
3. 사용자가 창호 사진과 벽체 사진을 업로드한다.
4. FastAPI가 사진을 검증한 뒤 Vision API에 일회성으로 전달하고, 구조화된 후보값을 수신한다.
5. 원본 사진은 분석 요청이 끝난 직후 서버의 메모리 또는 임시 파일 영역에서 폐기한다.
6. 사용자가 AI 후보를 확인, 수정, 확정한다.
7. 사용자가 MVP 지원 지역 목록에서 지역을 선택하고 서버가 검증된 HDD를 조회한다.
8. 서버가 기준값과 물리식으로 계산한다.
9. 사용자가 추정 연간 열손실, 개선 시나리오, 사진상 이상 흔적 안내를 확인한다.
10. 사용자가 진단 종료를 누르거나 브라우저 세션이 끝나면 클라이언트 임시 상태를 폐기한다. 서버에는 진단 이력이나 원본 사진을 남기지 않는다.

### 2.2 LiDAR의 지위

- LiDAR, RoomPlan, iOS 앱, 공간 스캔, 스캔 프레임 자동 추출은 이번 MVP 구현 범위가 아니다.
- 향후 확장을 고려해 입력 출처 필드는 둘 수 있다. 현재 구현값은 manual과 user_corrected만 허용한다.
- 미래 예약값 lidar는 저장 구조에만 남길 수 있으나, 이번 구현에서 생성, 업로드, 처리하지 않는다.
- iOS 스캐너 프로젝트, LiDAR 업로드 API, 딥링크를 구현 작업에 추가하지 않는다.
- 발표에서 LiDAR를 언급하면 향후 자동 공간 측정 확장 가능성으로만 언급한다. 현재 구현 기능처럼 시연하거나 주장하지 않는다.

### 2.3 사진 AI의 역할 경계

사진 AI는 면적을 자동 실측하지 않는다. 사진만으로 실제 길이, 면적, U값을 정확히 추정하지 않는다.

| 대상 | Vision API 후보 | 사용자 확정 | 계산에 쓰는 값 |
|---|---|---|---|
| 창호 사진 | 단창, 복층창, 삼중창, 판단불가, 사진 품질 | 대표 창호 유형, Low-E 선택값 | 사용자 확정 창호 유형과 Low-E |
| 벽체 사진 | 사진상 이상 흔적 후보 있음, 사진상 뚜렷한 이상 흔적 없음, 판단불가, 사진 품질 | 사진상 이상 흔적 여부 | 벽체 U값 계산에는 사용하지 않음 |
| 공간과 면적 | 처리하지 않음 | 치수, 창호 합산면적, 외기 접촉 벽체 합산면적 | 사용자가 입력하고 확정한 값 |

창호 유형과 손상 징후는 촬영 각도, 반사, 조명에 따라 오판 가능하다. 판단불가, 재촬영 필요, 사용자 확인 필요는 정상 결과로 설계한다.

## 4. 권장 기술 아키텍처

| 계층 | 권장 구성 | 책임 |
|---|---|---|
| 웹 클라이언트 | React, TypeScript, Vite, Vercel | 입력, 사진 촬영 또는 선택, 업로드 상태, AI 후보 확인과 수정, 결과 표시 |
| 프론트 라이브러리 | React Router, TanStack Query, React Hook Form, Zod, Tailwind CSS | 화면 전환, API 상태, 입력 검증, UI |
| API 서버 | Python, FastAPI, Uvicorn | 입력 검증, 사진의 일회성 Vision API 전달, 계산 요청, 결과 반환 |
| 백엔드 라이브러리 | Pydantic, SQLAlchemy 2, Alembic, psycopg, Pillow, python-multipart, OpenAI SDK, tenacity | 스키마, 기준 DB, 마이그레이션, 이미지 검증, 업로드, AI 호출, 재시도 |
| 관계형 DB | PostgreSQL | U값, HDD, 지원 지역, 기준 버전과 출처 등 정적 기준 데이터 |
| AI | Vision 입력과 Structured Output을 지원하는 외부 API | 사진 후보 분류만 담당 |
| 배포 | Vercel, AWS EC2 Docker, PostgreSQL 또는 RDS | 웹, API, 기준 DB |

### 4.1 GPU와 API 키

- Vision 모델은 외부 API로 사용한다. GreenScan의 EC2에 GPU 서버는 필요하지 않다.
- AI API 키는 FastAPI 서버의 비밀 환경변수에만 둔다. React 또는 Vercel에 키를 넣지 않는다.
- 모델명은 코드에 고정하지 말고 VISION_MODEL 같은 환경변수로 관리한다.
- OpenAI를 사용한다면 API 권한과 결제 또는 크레딧은 ChatGPT 구독과 별도로 확인한다.

### 4.2 사진 처리 흐름

React 웹에서 사진을 업로드한다. FastAPI는 파일 형식, 용량, 이미지 무결성과 EXIF 처리 정책을 검증한다. 검증된 사진은 Vision API에 바로 전달하고 구조화된 후보값만 응답한다. React는 후보값을 브라우저 임시 상태에 보관해 사용자의 수정 또는 확정을 받는다.

- 사진 원본을 S3, PostgreSQL, 서버 영구 디스크에 저장하지 않는다.
- FastAPI의 업로드 임시 파일 또는 메모리 버퍼는 Vision API 요청이 끝난 직후 닫고 폐기한다.
- 사용자가 분석 재시도를 원하면 같은 사진을 브라우저에서 다시 업로드한다. 서버가 원본 사진을 재사용해 재분석하지 않는다.
- 페이지 새로고침 후 사진 미리보기를 복원할 필요가 있으면 브라우저의 임시 상태만 사용한다. MVP는 새로고침 후 입력 복구를 보장하지 않는다.
- 화면에는 사진이 AI 분석을 위해 외부 API에 전송되고 GreenScan 서버에는 원본을 저장하지 않는다고 고지한다.

## 5. 임시 진단 흐름과 사용자 입력

### 5.1 임시 진단 상태

로그인 없는 서비스다. MVP에서는 서버 측 게스트 세션, 진단 이력, TTL 자동 삭제 작업을 구현하지 않는다.

- 사용자의 입력값, AI 후보값, 사용자 확정값, 계산 결과는 React 화면 상태에 임시 보관한다. sessionStorage를 사용하면 같은 탭의 새로고침 복구는 선택적으로 지원할 수 있으나, MVP 필수 기능은 아니다.
- FastAPI의 분석 API와 계산 API는 요청에 필요한 값을 받아 즉시 응답하는 방식으로 구현한다.
- 사용자가 진단 종료를 누르면 클라이언트 임시 상태를 지운다.
- 브라우저 탭을 닫거나 새로고침하면 진행 중 입력이 사라질 수 있으며, MVP에서는 복구를 보장하지 않는다.
- PostgreSQL에는 사용자 진단 이력, 사진 메타데이터, AI 분석 이력, 계산 결과를 저장하지 않는다.

### 5.2 필수 입력

| 범주 | 필드 | 규칙 |
|---|---|---|
| 대상 | 건물 유형, 대표 공간 유형 | 단독·다가구 또는 아파트만 허용 |
| 공간 | 가로, 세로, 높이, 바닥면적 | 길이는 m, 면적은 m². 바닥면적과 가로×세로의 검증 규칙 필요 |
| 창호 | 창호 합산면적, 대표 창호 유형, Low-E 선택 | 창호 면적은 0보다 커야 함. Low-E는 AI가 확정하지 않음 |
| 벽체 | 외기 접촉 벽체 합산면적, 기존 단열 상태 | 외기 접촉 여부와 면적은 사용자가 직접 확정 |
| 건물 조건 | 준공연도 구간 | 정확한 연도 대신 정책화된 구간값 사용 |
| 위치 | MVP 지원 지역 선택값, HDD 식별값 | 자유 시군구 입력이 아니라 검증된 지원 지역 목록에서 선택 |
| 선택 고지서 | 에너지원, 사용기간, 사용량, 단위 | 참고 비교용이며 핵심 계산 보정에는 사용하지 않음 |

벽체 계산 순면적은 아래 규칙을 사용한다.

외기 접촉 벽체 순면적 = 외기 접촉 벽체 합산면적 - 창호 합산면적

이 값이 0 이하이면 입력 오류다. 계산하지 말고 외기 접촉 벽체 면적과 창호 합산면적을 다시 확인하게 한다.

### 5.3 입력 출처

각 계산 요청의 입력에는 출처를 함께 담는다. 이 출처는 MVP에서 사용자 진단 이력으로 저장하지 않는다.

- manual: 사용자가 직접 입력
- user_corrected: 사용자가 AI 후보 또는 이전 값을 수정하고 확정
- lidar: 향후 예약값

현재 MVP에서는 lidar 값의 생성, 업로드, 처리를 구현하지 않는다.

## 6. Vision AI 상세 요구

### 6.1 사진 카테고리와 촬영 가이드

사진은 최소 두 카테고리로 구분한다.

1. window: 창호 전체가 가능한 한 잘 보이는 사진
2. wall: 외벽 또는 손상 의심 부위가 가능한 한 잘 보이는 사진

촬영 가이드 UI 요구사항:

- 창호는 프레임과 유리 면이 함께 보이게 안내한다.
- 벽체는 의심 부위가 흐리지 않게 안내한다.
- 어두움, 강한 반사, 과도한 원거리 사진은 재촬영을 안내한다.
- AI 분석 실패 또는 사진 미제출 시 사용자가 유형과 손상 여부를 수동 선택해 결과까지 진행할 수 있어야 한다.

### 6.2 구조화된 AI 응답 계약

Vision API의 자유 텍스트를 계산에 직접 사용하지 않는다. 백엔드는 응답을 검증 가능한 구조로 파싱하고 정규화한다.

최소 응답 필드:

| 필드 | 허용 값 또는 의미 |
|---|---|
| assessment_status | completed, unassessable, failed |
| photo_quality | usable, retake_required, unknown |
| component_type | window, wall, unknown |
| window_type_candidate | single, double, triple, unknown, not_applicable |
| visible_anomaly_candidate | suspected, none_observed, unassessable, not_applicable |
| needs_user_confirmation | 항상 true |
| reason_summary | 사용자에게 보여 줄 짧은 근거 설명 |

추가 규칙:

- single, double, triple은 후보값이다. 실제 창호 사양 확정값으로 저장하지 않는다.
- confidence 수치가 있더라도 물리적 측정 정확도를 뜻하지 않는다. 계산 자동 확정에 쓰지 않는다.
- AI가 정해진 스키마를 지키지 않으면 failed로 처리하고 수동 선택 폴백을 제공한다.
- 사진 품질 부족이면 재촬영을 우선 제안하되 사용자가 수동 선택으로 건너뛸 수 있어야 한다.
- AI 원본 응답과 정규화 후보값은 서버에 영구 저장하지 않는다. 계산에는 브라우저에서 사용자가 확정해 다음 계산 요청에 담은 값만 사용한다.

### 6.3 사용자 확정 규칙

계산 전 아래 값은 반드시 사용자 확정 상태여야 한다.

- 대표 창호 유형
- Low-E 선택값 또는 모름
- 사진상 이상 흔적 여부

사용자 확정값은 AI 후보값과 별도 필드로 프론트 임시 상태와 계산 DTO에 담는다. 계산 엔진은 사용자 확정값만 입력으로 받는다.

사진상 이상 흔적 후보는 현장 점검 권장 안내만 바꾼다. 이 값이 U값, 면적, 열손실 계산식, 연간 열손실 수치를 자동 수정해서는 안 된다.

## 7. 기준 데이터와 계산 규칙

### 7.1 현재 U값과 개선 목표 U값

현재 상태 추정 U값과 개선 목표 U값은 반드시 분리한다.

| 값 | 조회 조건 | 의미 |
|---|---|---|
| 현 상태 추정 U값: 창호 | 사용자 확정 창호 유형과 Low-E 선택 | 실제 측정 U값이 아닌 정책 테이블 기반 추정치 |
| 현 상태 추정 U값: 벽체 | 준공연도 구간과 기존 단열 상태 | 사진으로 단열재 상태를 판정한 값이 아님 |
| 개선 목표 U값 | 건물 기준 그룹, 기후구역, 부위, 기준 데이터 버전 | 개선 시나리오 비교용 목표값 |

### 7.2 고시와 별표 데이터

기준 데이터에는 기준명, 고시번호, 기준 버전, 시행일, 출처 문서, 적용 부위, 건물 구분, 기후구역, 조건, U값을 함께 관리한다.

- 2024년 고시 데이터는 데모 비교 기준 데이터 버전으로 고정해 사용할 수 있다. 최신 법정 기준 또는 법적 적합성 판정이라고 표현하지 않는다.
- 최종 데이터 시드 전에는 적용하려는 기준 버전과 최신 기준의 차이를 팀이 검증한다.
- 창호와 문 목표 성능은 별표 4, 외벽 등 건축 부위 목표 U값은 별표 1인지 실제 기준 원문으로 부위별 확인한다. 외벽과 창호를 모두 별표 4에서 조회한다고 가정하지 않는다.
- 기준값이 누락되면 임의 수치를 만들지 않는다. reference_data_missing 오류로 계산을 중단한다.

### 7.3 MVP 지원 지역과 HDD

- 전국 시군구 자유 입력과 전국 HDD 매핑은 MVP 범위가 아니다.
- 프론트는 서버의 검증된 지원 지역 목록만 선택지로 보여 준다.
- 팀은 데모에 쓸 소수 지역을 기준 원문과 HDD 출처 확인 후 시드한다. 정확한 지역 목록은 정책 데이터로 관리한다.
- 선택한 지원 지역 키로 HDD를 직접 조회한다.
- HDD 데이터는 버전과 출처를 보존한다.
- 지원하지 않는 지역은 입력을 받지 않는다. 화면에는 MVP 지원 지역 기준이라고 표시한다.

### 7.4 열손실 계산

연간 열손실 추정식:

annual_heat_loss_kwh = u_value × area_m2 × 24 × hdd ÷ 1000

계산 규칙:

1. 창호와 외기 접촉 벽체를 각각 계산한 뒤 합산한다.
2. 벽체는 외기 접촉 벽체 순면적을 쓴다.
3. 길이는 m, 면적은 m², U값은 W/m²·K, HDD는 K·day, 결과는 연간 kWh로 통일한다.
4. 천장, 바닥, 환기, 침기, 일사, 난방기기 효율, 거주자 사용 습관은 MVP에서 제외한다.
5. 화면은 이 한계를 결과 근처에 표시한다.

### 7.5 결과와 시나리오

- 기준선은 현 상태 추정 U값으로 계산한 창호와 외기 접촉 벽체의 추정 연간 열손실량이다.
- 시나리오는 한 부위 또는 복수 부위에 개선 목표 U값을 적용한 결과다.
- 각 시나리오에는 이름, 변경 부위, 연간 감소량, 절감률, 우선순위, 적용 기준 버전을 포함한다.
- 우선순위는 추정 열손실 감소량이 큰 순서다.
- 절감률의 분모는 기준선 열손실량이다.
- 절감률을 건물 전체 에너지 사용량 절감률로 표현하지 않는다.
- 비용과 견적 금액은 표시하지 않는다.
- 결과 화면의 핵심은 추정 연간 열손실량, 창호와 벽체 부위별 열손실량, 시나리오별 감소량과 감소율, 개선 우선순위다.
- 낮음, 보통, 높음 위험도 등급과 임의 임계값은 MVP에서 표시하지 않는다.

## 8. 상태 전이와 오류 처리

### 8.1 권장 상태

draft → input_pending → photo_pending → ai_analyzing → confirmation_required → calculation_ready → completed

각 단계에서는 recoverable_error 또는 failed가 가능하다. MVP에서 상태는 클라이언트 임시 흐름을 표현하며 서버의 진단 이력으로 저장하지 않는다.

| 상태 | 의미 | 다음 사용자 행동 |
|---|---|---|
| input_pending | 공간과 건물 조건 입력 중 | 필수값 입력 또는 수정 |
| photo_pending | 사진 업로드 또는 수동 선택 대기 | 사진 업로드, 수동 분류 선택 |
| ai_analyzing | Vision API 호출 중 | 진행 상태 조회 |
| confirmation_required | AI 후보 또는 수동값 확정 필요 | 수정과 확정 |
| calculation_ready | 계산 필수값 모두 확정 | 계산 실행 |
| completed | 결과 생성 완료 | 결과 확인 또는 진단 종료 |
| failed | 기준 데이터나 계산 등 복구 불가능한 실패 | 원인 확인 후 해당 단계 재시도 |

### 8.2 오류 분류

| 오류 | 사용자 경험 | 계산 진행 |
|---|---|---|
| 사진 형식, 용량, 손상 오류 | 재업로드 요청 | 불가 |
| 사진 품질 부족 | 재촬영 제안 또는 수동 선택 | 수동 확정 시 가능 |
| Vision API 일시 실패 | 재시도 안내 또는 수동 선택 | 수동 확정 시 가능 |
| Vision 응답 스키마 오류 | 수동 선택 폴백 | 수동 확정 시 가능 |
| 입력값 누락, 면적 모순 | 해당 입력 단계로 복귀 | 불가 |
| 기준 데이터 누락 | 오류 안내, 데이터 수정 필요 | 불가 |
| 브라우저 새로고침, 탭 종료 | 진행 중 입력과 결과가 사라질 수 있음 | 새 진단 시작 |

## 9. API와 DB 설계 지시

### 9.1 API 책임

세부 URL은 다음 설계 단계에서 확정한다. 단, 최소 책임은 반드시 분리한다.

- 지원 지역과 기준 데이터 조회
- 창호 또는 벽체 사진의 일회성 분석
- 건물과 공간의 최종 확정 입력 검증
- 계산 실행과 결과 반환
- 선택 고지서 참고 비교 요청

권장 API 흐름:

1. 프론트가 지원 지역 목록을 조회한다.
2. 프론트가 사진을 분석 API에 전달하고 AI 후보 응답을 받는다.
3. 프론트가 사용자 확정값과 공간 입력을 계산 API에 한 번에 전달한다.
4. 계산 API가 결과를 반환하고, 프론트가 같은 브라우저 세션에서 표시한다.

API 규칙:

- 프론트는 AI API 키와 기준 U값 테이블 전체를 직접 보유하지 않는다.
- 사진 분석 API는 사진 카테고리와 원본 파일을 받고, 사진을 보관하지 않은 채 후보값과 품질 상태를 반환한다.
- AI 분석은 MVP에서 짧은 동기 요청으로 구현해도 된다. 별도 메시지 큐나 분석 상태 저장을 강제하지 않는다.
- 계산 API는 사용자 확정 전 AI 후보를 받아 계산하지 않는다.
- 계산 응답은 계산 버전, 기준 데이터 버전, 입력 출처를 포함한다.

### 9.2 DB 책임

MVP PostgreSQL은 사용자 진단 이력을 저장하는 DB가 아니라 계산 기준 데이터를 제공하는 DB다. 정확한 테이블명은 설계 단계에서 결정한다.

| 도메인 | 반드시 보존할 정보 |
|---|---|
| 지원 지역 | 표시명, 지원 여부, HDD 조회 키, 기후 조건 설명, 데이터 버전 |
| 기준 데이터 | 기준명, 고시번호, 별표와 부위, 조건, 버전, 출처, U값 또는 HDD |
| 현재 상태 U값 정책 | 창호 유형, Low-E, 준공연도 구간, 단열 상태, U값, 정책 버전 |
| 개선 목표 U값 정책 | 건물 기준 그룹, 기후구역 또는 지원 지역, 부위, U값, 기준 버전 |
| 계산 정책 | 계산식 버전, 시나리오 정의, 결과 문구 정책 |

사진 파일, 사진 메타데이터, AI 분석 이력, 사용자 진단 이력, 계산 결과는 MVP PostgreSQL에 저장하지 않는다.

## 10. 백엔드 역할 분담과 통합

백엔드 3명 기준 책임 경계:

| 역할 | 책임 | 다른 역할에 넘기는 것 |
|---|---|---|
| BE-A: 입력, API 흐름 | 공간과 건물 입력 검증, 지원 지역 조회, 계산 요청 조합, 프론트와 공통 DTO | 정규화된 확정 계산 입력 |
| BE-B: Vision 연동 | 사진의 일회성 Vision API 호출, 구조화된 응답 검증, 사진 품질과 후보값, 재업로드 폴백 | 사진별 후보값과 품질 상태 |
| BE-C: 기준 데이터, 계산 | U값, HDD, 지역 매핑, 시나리오, 결과 근거와 단위, 버전 검증 | 계산 결과, 기준 데이터 오류 |
| 통합과 배포 담당 | 공통 계약, 환경변수, Docker와 EC2 배포, CORS, Mock 제거, E2E와 데모 데이터 | 최신 명세와 통합 완료 흐름 |

통합 담당은 마지막 날 배포만 하는 역할이 아니다. 다음을 초기에 고정한다.

1. 공통 입력 스키마와 단위
2. AI 후보와 사용자 확정값 분리 방식
3. 사진의 일회성 처리와 원본 폐기 방식
4. 계산 요청과 결과 형식
5. 오류 코드와 화면 복귀 단계
6. 개발과 배포 환경변수, 지원 지역 기준 데이터 시드

### 10.1 구현 순서

1. 수동입력 → 계산 → 결과를 Mock 기준 데이터로 먼저 완주한다.
2. 실제 U값, HDD 기준 데이터 시드와 검증을 붙인다.
3. 지원 지역 목록과 검증된 HDD 시드 데이터를 붙인다.
4. 사진 업로드 → Vision API 일회성 분석 → 원본 폐기를 연결한다.
5. Vision 후보값 → 사진 품질 판단 → 재촬영 또는 사용자 확정 UI를 연결한다.
6. 고지서 참고 비교와 촬영 가이드의 고도화는 Must 흐름이 완성된 뒤 붙인다.
7. LiDAR는 위 순서를 지연시키지 않는 확장으로만 검토한다.

## 11. MVP 우선순위

### Must

- React의 임시 상태 또는 sessionStorage로 한 번의 진단 흐름 유지
- 단독·다가구주택 또는 아파트 선택과 서버의 기준 그룹 매핑
- 대표 공간 수동 치수, 면적, 외기 접촉 벽체, 창호 합산면적 입력 검증
- 검증된 MVP 지원 지역 목록 선택과 HDD 조회
- 창호와 벽체 사진 업로드, Vision API로 일회성 전달, 원본 즉시 폐기
- Vision API 구조화 후보 분류
- 사진 품질 평가와 재촬영 필요 처리, AI 실패 또는 판단 불가 시 수동 선택 폴백
- AI 후보 확인, 수정, 수동 확정 UI
- 현재 추정 U값과 개선 목표 U값 분리 조회
- HDD 기반 열손실 계산, 시나리오 2~3개, 우선순위
- 사진상 이상 흔적 안내와 열손실 계산의 분리
- 추정 연간 열손실량, 부위별 열손실, 시나리오별 감소량과 감소율 표시. 위험도 등급은 표시하지 않음

### Should

- 1개월 전기와 가스 사용량 참고 비교
- 사진 촬영 가이드 문구와 예시 고도화
- Vision API 재시도와 분석 진행 UI 고도화

## 12. 통합 테스트와 완료 기준

아래 시나리오는 Must 완료 전 반드시 통과해야 한다.

1. 기본 완료: 단독·다가구주택의 대표 공간 입력 → 사진 업로드 → 수동 또는 AI 확정 → 계산 → 결과
2. 아파트 기준 매핑: 아파트 선택 시 개선 목표 U값 조회에 공동주택 그룹이 적용됨
3. AI 수정 반영: AI가 복층창 후보를 반환해도 사용자가 단창으로 수정하면 계산은 단창 확정값을 사용함
4. 사진 품질 부족: 재촬영 필요가 반환되어도 사용자가 수동 선택 후 결과까지 갈 수 있음
5. Vision 장애: API 시간초과나 스키마 오류에도 AI 실패가 전체 진단 실패가 되지 않음
6. 면적 모순: 벽체 순면적이 0 이하이면 계산이 차단되고 입력 수정이 안내됨
7. 사진상 이상 흔적 분리: 이상 흔적 안내 유무가 같은 U값과 면적 입력의 열손실 수치를 바꾸지 않음
8. 고지서 미입력: 핵심 결과가 생성되고 추정치임을 표시함
9. 원본 폐기: 사진 분석 API 처리 후 서버 영구 저장소와 PostgreSQL에 원본 사진 또는 분석 이력이 남지 않음
10. 지원 지역 제한: 지원 목록 밖의 지역은 선택할 수 없고, 선택된 지역의 검증된 HDD만 계산에 사용함
11. 기준 누락: U값 또는 HDD 기준 데이터가 없으면 임의 계산 대신 명시적 오류가 반환됨

## 13. 에이전트 산출물 요구

이 지시문을 기반으로 API 명세나 DB 설계를 생성할 때는 반드시 아래 산출물을 함께 제공한다.

- MVP 기준 API 목록과 요청, 응답 DTO
- 상태 전이표와 오류 코드
- 기준 데이터 DB의 ERD 또는 DBML, 테이블별 제약과 인덱스
- 원본 사진의 일회성 전달, 임시 파일 폐기, 외부 AI 전송 고지 처리
- Vision API 요청 프롬프트의 역할 경계와 구조화 응답 스키마
- 지원 지역, 기준 U값, HDD 시드 데이터의 버전, 출처 필드
- 프론트와 백엔드가 공유하는 Mock JSON
- 12장의 통합 테스트 케이스

에이전트는 이 문서에 없는 기능을 멋대로 확장하지 말고, 추가 제안은 반드시 후속 확장으로 분리한다.

## 14. 최종 제품 메시지

현재 MVP 메시지는 다음으로 고정한다.

사진 기반 AI 건축요소 후보 분류와 사용자 입력, 검증된 지원 지역의 공공 기준값과 물리식을 결합해 노후주택 대표 공간의 추정 연간 열손실과 그린리모델링 개선 우선순위를 제시하는 사전진단 서비스

LiDAR는 현재 MVP의 전제가 아니다. 사진 AI는 측정이나 인증 도구가 아니라, 사용자가 확인하고 수정할 수 있는 건축요소 상태 후보를 빠르게 제공하는 보조 판단 도구다.
