# GreenScan PRD Agent Directive v8

## 문서 목적과 우선순위

이 문서는 GreenScan의 API 명세, DB 설계, 백엔드 모듈, 프론트엔드 흐름, 테스트와 구현 계획을 만들거나 검토하는 에이전트의 최상위 지시문이다.

- 기준 문서: GreenScan PRD Agent Directive v7 (`GreenScan_PRD_v7.md`, 이 저장소에는 v8로 대체됨)
- 이번 버전: v8
- v8의 핵심 변경: 디자인팀 시안 검토 후 PM이 의도적으로 결정한 이탈 사항을 문서에 정식 반영한다. **로그인/계정 도입**(v7의 "로그인 없는 서비스" 원칙 폐기), 홈·지도·추천·저장·마이페이지 하단 탭 구조 추가, 카카오맵 연동(주소 검색 기반 지역 판단), 결과 화면의 등급·긴급도 배지와 러프 견적 범위 텍스트를 조건부(비확정 고지 필수)로 허용한다.
- v7의 물리 계산 원칙(U값/HDD 계산식, 대표 공간 1개 기준, 사진 AI는 후보 분류기라는 경계, 건물 전체 진단 금지, 상가 제외)은 **그대로 유지**한다. 바뀐 것은 계정·이력·위치 기반 부가 기능이지, 진단 계산의 정확성·표현 원칙이 아니다.
- 이 문서의 근거가 된 논의 기록은 `docs/prd-v7-deviations.md`(작업 브랜치 `feature/fe-mockup`)에 남아 있다. 세부 조건이나 "왜 이렇게 정했는지"가 더 필요하면 그 문서를 참고할 것.
- **v8.1 수정 (2026-09-11, BE-A 담당자가 PM과 직접 확인 후 반영)**: 아래 5가지를 v8 내용 위에 덮어쓴다.
  1. 로그인 방식 확정 — **JWT 미사용**, DB에 미리 시드해둔 소수 계정만 사용(자체 회원가입·소셜 로그인 없음). 5장 갱신.
  2. 진단 이력 저장 — v8 그대로 Must 유지 (변경 없음).
  3. 지도 검색 지원 범위 — **서울만** 지원. 김포 등 타 지역 지도 검색은 이번 범위 아님(단, 계산용 `supported_regions`의 서울/김포 목록 자체는 별개 결정이라 유지). 4.1·6.1절 갱신.
  4. **참고용 에너지 효율 레벨(LV.n) 표시를 제외한다.** v8이 조건부 허용했던 것을 다시 철회 — "의미 없는 숫자"라 판단. 1.2·1.3·9.1·13장 갱신.
  5. **견적(러프 범위 텍스트 포함) 표시를 제외한다.** v8이 조건부 허용했던 것을 다시 철회. 1.2·1.3·9.1·13장 갱신.
  6. 저장(즐겨찾기) 탭 — 범위를 단순 즐겨찾기 토글로 확정(그 이상 기능 없음). 2.2절 갱신.
- **v8.2 수정 (2026-09-11, 서경대 해커톤 멘토링 — 장문수 교수님 피드백 반영)**: 아래 3가지를 v8.1 내용 위에 덮어쓴다. (같은 자리에서 나온 "AI 업체매칭/견적비교 플랫폼으로 전면 전환" 제안은 **채택하지 않는다** — 계산 엔진·기준데이터·Vision 분류 구조를 유지하는 현재 방향을 그대로 가져가되, 아래 결과 표현·타겟층만 조정한다.)
  1. **정성적 등급(긴급/주의/권장) 표시를 재도입한다.** v8.1에서 철회했던 것을 다시 허용 — 단, 숫자 레벨(`LV.n`)과 견적 표시는 v8.1 그대로 계속 제외한다. 등급은 반드시 "참고용 추정치이며 실제와 다를 수 있다"는 고지와 함께 표시한다. 원칙 9, 1.3, 9.1, 13장 갱신.
  2. **타겟층을 소유자+세입자 병기로 확대한다.** 기존 "노후주택 소유자" 중심에서, 세입자도 결과를 보고 집주인에게 개선을 요청하는 용도로 쓸 수 있게 한다. 진단·계산 로직은 동일하고, 화면 문구와 온보딩만 두 타겟 모두에 맞게 조정한다. 3장 갱신.
  3. **결과 화면 표현 원칙 추가**: 정밀 수치(%, 소수점)를 전면에 내세우지 않고 "총량이 위험/보통/양호 수준인지"를 먼저 보여준 뒤, 부위별 비율(파이차트 등 비율 시각화)과 개선 우선순위(감소량 순, 강조 표시)를 그다음에 보여준다. "나올 수 없는 정밀도의 계산"처럼 보이는 표현은 피한다. 9.1절 갱신.

에이전트는 아래 원칙을 반드시 따른다.

1. 본 문서의 v8 결정이 v7의 무상태·비로그인 요구보다 우선한다.
2. 바뀌지 않은 v7 핵심 범위는 유지한다. 대표 공간 1개, 지원 건물, U값과 HDD 계산, 사용자 확정, 결과 표현은 유지 대상이다. 단, **원본 사진은 여전히 서버에 저장하지 않는다.** 진단 이력은 이제 로그인한 계정에 한해 저장한다(5장 참고). 저장 방식(스키마)은 BE가 별도로 확정한다.
3. 기준이 모호할 때 그럴듯한 수치나 정책을 임의로 확정하지 않는다. 필요한 값은 정책 확정 필요로 분리하고 DB에서 버전 관리할 수 있게 설계한다. 이번 버전에서 새로 열린 정책 확정 필요 항목(로그인 방식, 등급 산정 로직, 견적 근거값, 지도 공유 범위 등)은 문서 곳곳에 명시했다.
4. 사진 AI는 후보 분류기다. AI 원본 응답이나 모델 신뢰도만으로 계산값을 확정하면 안 된다.
5. 실제 U값, 단열재 상태, 구조 안전성, 누수 원인, 건물 전체 에너지 사용량을 사진만으로 진단하는 것처럼 구현하거나 표현하지 않는다.
6. 공식 인증, 건물 전체 진단, 상가 지원은 새 기능으로 추가하지 않는다. **v8.1: 비용·견적은 러프 범위 텍스트를 포함해 이번 범위에서 완전히 제외한다.** (v8이 조건부 허용했던 것을 철회 — 아래 v8.1 수정 공지 참고)
7. 계산은 서버 계산 엔진이 수행한다. 프론트엔드는 계산식을 중복 구현하지 않는다.
8. MVP에 GPU 서버, 자체 모델 학습, YOLO, 벡터 DB, LangChain, Redis 또는 Celery를 기본 전제로 넣지 않는다.
9. **v8.2: 정성적 등급(긴급/주의/권장) 표시는 허용, 숫자 레벨(`LV.n`)은 계속 제외한다.** v8.1에서 등급 전체를 철회했었으나, 멘토링 피드백(정밀 수치보다 직관적 등급이 소통에 유리하다)을 반영해 정성적 등급만 재도입한다(2026-09-11). 등급 표시는 **반드시 "참고용 추정치이며 실제와 다를 수 있다"는 고지를 동반**해야 하며, 산정 로직(임계값)은 이 문서에서 확정하지 않으며 BE-C가 정책으로 확정하기 전까지는 프론트/디자인 어디에도 실제 로직인 것처럼 하드코딩하지 않는다. 우선순위(감소량 큰 순서) 자체는 v7부터 유지해온 핵심 결과이므로 계속 표시한다.
10. **사용자 간 데이터 공유(지도에서 다른 사용자의 진단 정보를 보여주는 등)는 명시적 동의 없이 노출하지 않는다.** 공유 범위, 데이터 항목, 동의 UX는 이번 버전에서 확정하지 않고 보류한다(6.3절 참고) — 설계·구현 착수 전 별도 정책 확정이 선행되어야 한다.

## 1. 제품 정의

### 1.1 한 줄 정의

GreenScan은 노후 단독·다가구주택 및 아파트의 대표 공간 1개를 대상으로, 사용자가 입력한 공간 정보와 창호·벽체 사진의 AI 후보 분류를 결합해 추정 연간 열손실과 그린리모델링 개선 우선순위를 제시하는 전문가 진단 이전 단계의 1차 사전진단 서비스다. v8부터는 로그인한 사용자에 한해 진단 기록을 계정에 보관하고, 홈 화면과 지도를 통해 접근할 수 있다.

### 1.2 사용자가 얻는 것

- 대표 공간 1개 기준의 창호와 외기 접촉 벽체 연간 전도 열손실 추정치
- 창호 개선, 벽체 개선, 복합 개선 등 2~3개 시나리오의 추정 감소량과 절감률
- 추정 열손실 감소량이 큰 순서의 개선 우선순위
- 사진상 이상 흔적 후보에 대한 별도 현장 점검 권장 안내
- 결과에 사용된 사용자 입력, AI 후보, 기준 데이터 버전, 계산 근거
- (로그인 시) 과거 진단 기록 조회, 홈/마이페이지에서 최근 분석 이력 확인
- **(v8.2)** 참고용 정성적 등급(긴급/주의/권장) — 반드시 "참고용 추정치, 실제와 다를 수 있음" 고지 동반

### 1.3 절대 표현 금지

- 건물 전체 에너지 사용량 또는 고지서 사용량을 정확히 예측, 보정, 검증했다.
- 공식 에너지 등급 또는 법적 적합성 판정을 제공한다.
- 사진 AI가 실제 U값, Low-E 여부, 단열재 유무, 구조 안전성, 균열이나 누수 원인을 확정했다.
- 사진상 이상 흔적 후보 때문에 열손실 수치가 자동으로 증가했다.
- 한 방 결과가 아파트 세대 전체 또는 건물 전체 결과다.
- (v8.1→v8.2 일부 수정) 숫자 레벨(`LV.n`)을 표시한다 — 이번 범위에서 완전히 제외. 단, 정성적 등급(긴급/주의/권장)은 **고지 문구를 동반하면 허용**한다(원칙 9 참고) — 고지 없이 단정적으로 표시하는 것만 금지.
- (v8.1) 견적 금액을 러프 범위 텍스트로도 표시한다 — 이번 범위에서 완전히 제외.
- 동의하지 않은 사용자의 진단 정보를 다른 사용자에게 노출한다.

결과 이름은 GreenScan 추정 연간 열손실 분석 또는 이와 동등하게 비공식 추정치임을 드러내는 표현을 쓴다. 결과 화면에는 이 방 기준을 명시한다.

## 2. v7에서 v8로 바뀐 MVP 범위

### 2.1 기본 진단 흐름 (변경 없음, 진입 경로만 추가)

1. (신규) 사용자가 로그인한다 — 로그인 방식은 5장 참고, 미확정.
2. (신규) 홈 화면에서 "AI 진단 시작하기"를 누른다.
3. 사용자가 건물 유형과 대표 공간을 선택한다.
4. 사용자가 대표 공간의 가로, 세로, 높이, 창호 합산면적, 외기 접촉 벽체 합산면적을 입력한다.
5. 사용자가 창호 사진과 벽체 사진을 업로드한다.
6. FastAPI가 사진을 검증한 뒤 Vision API에 일회성으로 전달하고, 구조화된 후보값을 수신한다.
7. 원본 사진은 분석 요청이 끝난 직후 서버의 메모리 또는 임시 파일 영역에서 폐기한다. **(변경 없음 — 로그인 도입과 무관하게 원본 사진은 여전히 저장하지 않는다.)**
8. 사용자가 AI 후보를 확인, 수정, 확정한다.
9. 사용자가 MVP 지원 지역 목록에서 지역을 선택하거나, (신규) 카카오맵 주소 검색으로 지역을 자동 판별한다 — 6장 참고. **(v8.1) 카카오맵 주소 검색은 서울 지역만 지원한다.**
10. 서버가 기준값과 물리식으로 계산한다.
11. 사용자가 추정 연간 열손실, 개선 시나리오, 개선 우선순위, 사진상 이상 흔적 안내를 확인한다. **(v8.1: 등급/긴급도 배지, 레벨, 견적 표시는 빠짐)**
12. (신규) 로그인 상태라면 이 진단 결과가 계정에 귀속되어 저장되고, 마이페이지/홈에서 다시 조회할 수 있다. 비로그인 이용 가능 여부는 미확정(5장 참고).

### 2.2 앱 구조 — 하단 탭 (신규)

디자인팀 시안 검토 후 추가된 구조. 하단 탭 5개:

| 탭 | 역할 | 상태 |
|---|---|---|
| 홈 | "AI 진단 시작하기" 진입점 + 최근 분석한 방 목록 | 이번 버전에 포함, 목록은 계정 기반 |
| 지도 | 카카오맵 연동 — 6장 참고 | **(v8.1) 서울 지역만 주소 검색·지역 판별 지원.** 주변 사용자 공유는 보류 |
| 환경 뉴스 | 그린리모델링/에너지 절약 관련 뉴스·콘텐츠 피드 (기존 "추천" 탭에서 명칭·성격 변경) | 내용 미정, 정책 확정 필요 |
| 저장 | 즐겨찾기 토글 (design 시안의 하트 아이콘) | **(v8.1 확정) 단순 즐겨찾기만.** 그 이상 기능 없음 |
| 마이페이지 | 프로필, 진단 기록, 계정 설정, 로그아웃 | 이번 버전에 포함 |

이 탭 구조는 v7의 "단일 진단 위저드 흐름"을 감싸는 앱 셸이다. 진단 흐름(공간입력→사진→AI확인→계산→결과) 자체의 화면 순서와 계산 로직은 바뀌지 않는다.

### 2.3 LiDAR의 지위

- iOS 앱이 RoomPlan으로 공간을 스캔하고, 사용자가 확인·수정한 치수와 면적을 기존 계산 API 형식으로 전송한다.
- 백엔드는 LiDAR 원본이나 RoomPlan 결과를 직접 분석하지 않으며, 프론트에서 확정된 계산 입력만 받는다.
- 공간 치수(`space`)의 입력 출처는 `manual`, `user_corrected`, `lidar`를 허용하며 출처에 따라 계산식을 변경하지 않는다. LiDAR로 얻을 수 없는 사용자 확인값이 함께 들어가는 창호·벽체 입력은 `manual`, `user_corrected`만 사용한다.

### 2.4 사진 AI의 역할 경계 (변경 없음)

v7과 동일. 창호 사진 → 창호 유형/품질 후보, 벽체 사진 → 이상 흔적 후보(있음/없음/판단불가). 계산에 쓰는 값은 사용자 확정값만.

벽체 이상 흔적의 `reason_summary` 예시에 "곰팡이로 추정되는 흔적 → 습도가 높을 가능성" 같은 문구를 쓸 수 있다 — 다만 이것도 원인을 확정하는 것이 아니라 현장 점검 권장 안내 수준을 유지해야 하며, U값·면적·열손실 계산에는 영향을 주지 않는다.

## 3. 대상 및 진단 범위 (v8.2: 타겟층 확대)

v7과 동일. 단독·다가구주택/아파트, 대표 공간 1개. 상가, 공용부, 세대 전체 진단은 여전히 제외 대상이다. **디자인 시안에 있던 1,000㎡ 이상 상업·업무·공공 건물 지원은 이번 버전에도 반영하지 않는다.**

**(v8.2, 2026-09-11 멘토링 반영)** 사용자 대상을 **소유자 + 세입자 병기**로 확대한다.
- 소유자: 자기 집 개선 우선순위 파악 목적 (기존과 동일)
- 세입자: 거주 중인 집의 상태를 파악해 집주인에게 개선을 요청하는 근거 자료로 사용 — 계산·진단 로직은 소유자와 동일, **화면 문구·온보딩만 두 타겟 모두를 포괄하도록 조정**한다 (예: "우리 집" 대신 "이 집" 같은 중립적 표현, 소유 여부를 묻지 않음).
- 이 변경이 로그인 계정 구조나 계산 로직에 미치는 영향은 없다 — 순수하게 문구/온보딩 레벨의 조정이다.

### 4.1 카카오맵 연동 범위 (신규, 정책 확정 필요 다수)

- **이번 범위**: 사용자가 주소를 검색하면 카카오맵(로컬/주소 검색 API)으로 좌표를 얻고, 그 좌표가 지원 지역 안에 있는지 판별해 HDD 조회에 사용한다. **(v8.1 확정) 지도 주소 검색은 서울만 지원한다** — 좌표가 서울 밖이면 미지원 지역으로 처리한다. 지도에는 "내가 최근 검색한 지역" 핀을 표시할 수 있다.
- **보류 (이번 범위 아님)**: "동의한 주변 사용자의 건물 정보(건축연도 등)를 지도에 표시"하는 기능은 PM이 명시적으로 보류했다. 아래가 모두 확정되기 전까지 설계·구현에 착수하지 않는다.
  - 정확히 어떤 데이터 항목을 노출할지 (건축연도만? 등급까지? 정확한 주소 노출 여부?)
  - "동의"의 UX — 언제, 어떻게 동의를 받고 철회는 어떻게 할지
  - "주변"의 정의 — 반경, 위치 정밀도(정확한 건물 좌표 vs 흐려진 좌표)
  - 이 데이터가 개인정보에 해당하는지, 비식별화가 필요한지
- 카카오맵 API 키는 FastAPI 프록시를 통해서만 쓰는지, 프론트에 공개 키를 직접 노출해도 되는지도 확인 필요(카카오맵 JS SDK는 통상 도메인 제한된 공개 키를 프론트에 둔다 — 이번 프로젝트에 적용 가능한지 검토).

## 5. 계정과 로그인 (신규 — v7의 "로그인 없는 서비스" 원칙 폐기)

v7 5.1절 "로그인 없는 서비스다. MVP에서는 서버 측 게스트 세션, 진단 이력, TTL 자동 삭제 작업을 구현하지 않는다"는 **더 이상 유효하지 않다.**

- **로그인 방식 확정 (v8.1, 2026-09-11 PM 확인)**: JWT를 쓰지 않는다. 자체 회원가입 플로우와 소셜 로그인도 없다. **DB에 미리 시드해둔 소수의 계정만 로그인에 사용한다** (운영자가 계정을 미리 만들어 둠). 세션 관리는 JWT가 아닌 방식(서버 세션/DB에 저장된 opaque 토큰 등)으로 구현한다 — 구체적인 세션 저장 방식(쿠키 vs 헤더, 토큰 만료 정책)은 BE-A가 구현 시 정하되 자체 서명 JWT는 쓰지 않는다.
- 비로그인 상태에서도 진단 자체(계산까지)를 이용할 수 있는지, 아니면 로그인이 필수인지도 **미확정**. 확정 전까지는 "로그인 후 이용"을 기본 가정으로 설계하되 화면 흐름에 비로그인 우회 가능성을 완전히 막아두지 않는다.
- 로그인한 사용자의 진단 결과(입력값, 확정값, 계산 결과 — **원본 사진은 제외**)는 계정에 귀속되어 서버에 저장된다. 이는 v7 9.2절의 "PostgreSQL에는 사용자 진단 이력을 저장하지 않는다"는 규칙을 대체한다.
- 저장 스키마(사용자 테이블, 진단 이력 테이블, 보관 기간)는 `docs/db-spec.md`에서 별도로 설계한다.
- **원본 사진 무저장 원칙은 로그인 도입과 무관하게 그대로 유지한다.** 계정에 저장되는 것은 사용자 확정값과 계산 결과이지 사진 원본이 아니다.
- 마이페이지(2.2절)에서 진단 기록 조회, "진단 기록 저장 끄기" 같은 옵트아웃, 로그아웃을 제공한다. (계정이 미리 시드되어 있고 자체 가입이 없으므로 "계정 정보 수정"은 이번 범위에서 제외)

## 6. 지도와 추천 탭 상세

### 6.1 지도 탭 — 확정 범위

- 카카오맵으로 주소를 검색해 지원 지역 여부를 자동 판별 (4.1절)
- **(v8.1 확정) 검색 지원 지역은 서울만.** 서울 밖 주소는 미지원 지역으로 안내.
- 내가 최근 검색/진단한 지역을 지도 핀으로 표시

### 6.2 지도 탭 — 보류 범위

동의한 주변 사용자 정보 공유 기능은 4.1절에 정리된 미확정 항목이 모두 정책으로 확정되기 전까지 **설계도, 구현도 시작하지 않는다.** API 명세나 DB 스키마에도 이 기능을 위한 테이블/필드를 임의로 미리 만들지 않는다 — 확정된 뒤에 그때 추가한다.

### 6.3 환경 뉴스 탭

기존 "추천" 탭에서 명칭과 성격을 변경 — 개선 시공 옵션이나 협력사를 추천하는 탭이 아니라, 그린리모델링·에너지 절약 관련 뉴스/콘텐츠를 보여주는 탭으로 방향을 바꿨다. 구체적으로 무엇을 보여줄지(자체 제작 콘텐츠? 외부 뉴스 큐레이션/RSS? 사용자 진단 결과와 연계된 맞춤 콘텐츠?), 콘텐츠 소스와 업데이트 주기는 PM이 아직 정하지 않았다. **정책 확정 필요 — 이 문서는 탭의 존재와 성격(추천/영업성 콘텐츠가 아니라 정보성 뉴스)만 기록하고 세부 내용은 비워둔다.**

## 7. 임시 진단 흐름과 사용자 입력 (v7 5장 계승, 로그인 반영)

### 7.1 진단 상태

### 7.3 입력 출처

`manual`, `user_corrected`, `lidar`를 실제 입력값으로 허용한다. LiDAR 측정값도 사용자가 확인한 최종 면적을 기존 계산 API에 전달하며, 백엔드는 모든 입력 출처에 동일한 면적 검증과 계산식을 적용한다.

## 9. 기준 데이터와 계산 규칙 (물리 계산은 변경 없음)

### 9.1 결과와 시나리오 (v8.2: 표시 순서·방식 갱신)

- 기준선, 시나리오, 우선순위, 절감률 **산출 로직(계산 엔진)은 v7과 동일** — 이번 변경은 전부 표시 방식에 관한 것이며 API 응답 구조나 계산식을 바꾸지 않는다.
- **(v8.1, 유지) 러프 견적 범위 텍스트, 숫자 레벨("LV.n")은 이번 범위에서 계속 제외한다.**
- **(v8.2) 정성적 등급(긴급/주의/권장)은 고지 문구와 함께 허용한다** (원칙 9 참고). 산정 임계값(예: 기준선 대비 몇 % 손실이면 "긴급"인지)은 이 문서가 확정하지 않는다 — BE-C가 정책으로 확정하기 전까지는 프론트/디자인에 실제 로직처럼 하드코딩하지 않는다. `docs/db-spec.md` 8장에 정책 확정 필요 항목으로 등록한다.
- **(v8.2) 결과 화면 표시 순서 권장안** (멘토링 피드백: "정밀 수치를 앞세우면 신뢰를 잃는다, 직관적으로 먼저 보여주고 세부는 그다음"):
  1. 총량 수준(등급: 긴급/주의/권장) — 정밀 %보다 먼저, 가장 크게
  2. 부위별 비율 (파이차트 등 비율 시각화) — "양이 아니라 비율"임을 명확히 표기
  3. 개선 시나리오별 우선순위 — 감소량 큰 순서, 색상/진하기로 강조
  4. 세부 수치(kWh, %) — 필요한 사람만 더 보도록 하단/상세보기로 배치
  - 이 순서 규정은 **프론트 표시 순서에 대한 권장안**이며 API 응답 필드 자체를 이 순서로 강제하지 않는다 — 기존 `baseline`/`scenarios` 필드를 프론트가 이 순서로 재배열해 보여주면 된다.
- 절감률의 분모는 여전히 기준선 열손실량이며, 건물 전체 에너지 사용량 절감률로 표현하지 않는다.

## 11. API와 DB 설계 지시 (계산/기준데이터 부분 변경 없음, 계정 영역 신규)

v7 9장의 API 책임 분리, 사진의 일회성 처리, 계산 API 규칙은 동일하게 유지한다. 아래를 추가한다.

## 14. 통합 테스트와 완료 기준 (v7 유지 + 추가 필요)

v7 12장의 11개 시나리오는 계산 로직이 바뀌지 않았으므로 그대로 유효하다. 아래는 v8에서 추가로 필요한 시나리오이며, **이 문서는 구체적 테스트 케이스까지는 작성하지 않는다** — 로그인/지도 정책이 확정된 뒤 별도로 작성한다.

- 로그인/로그아웃, 진단 이력이 계정에 정상 귀속되는지
- DB에 시드되지 않은 계정으로는 로그인이 거부되는지 (자체 가입 경로가 없음을 확인)
- 비로그인 상태에서의 동작(이용 가능 여부 확정 후)
- 카카오맵 주소 검색 → 서울 내 지역은 정상 판별, 서울 밖 주소는 미지원 지역으로 처리되는지
- 결과 화면에 등급/레벨/견적이 어디에도 표시되지 않는지 (v8.1 제외 확인)
- 원본 사진이 로그인 여부와 무관하게 여전히 저장되지 않는지 (v7 통합테스트 9번의 연장)

## 16. 최종 제품 메시지 (갱신)

현재 MVP 메시지는 다음으로 고정한다.

사진 기반 AI 건축요소 후보 분류와 사용자 입력, 검증된 지원 지역의 공공 기준값과 물리식을 결합해 노후주택 대표 공간의 추정 연간 열손실과 그린리모델링 개선 우선순위를 제시하는 사전진단 서비스. 로그인한 사용자는 진단 기록을 계정에 보관하고 지도에서 다시 확인할 수 있다.

LiDAR는 현재 MVP의 전제가 아니다. 사진 AI는 측정이나 인증 도구가 아니라, 사용자가 확인하고 수정할 수 있는 건축요소 상태 후보를 빠르게 제공하는 보조 판단 도구다. **(v8.2)** 결과 화면은 숫자 레벨·견적 없이, 고지 문구를 동반한 정성적 등급(긴급/주의/권장)과 추정 연간 열손실량·개선 우선순위를 제시한다. 소유자뿐 아니라 세입자도 대상으로 한다.
